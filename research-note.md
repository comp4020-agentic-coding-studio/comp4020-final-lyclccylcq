# Building a Workflow Around AI Coding

If I had to say what changed the most for me in 2026, my answer would definitely be AI agents. During 2025–26, I found that I could ask them to do more and more. As a student who studied software engineering as an undergraduate, I started thinking about what AI coding actually brings us as developers. After ten months of learning and practice, I think I have my own answer.

For me, the most important change is building a whole new workflow around AI. My answer to what good agentic development should look like is to let AI do much of the implementation, keep the developer in charge of decisions, and build the workflow around verification and testing.

There is a reasonable objection here: software engineering already has TDD, code review and continuous integration, so why should using AI require a new workflow? [Nagappan et al.](https://research.ibm.com/publications/realizing-quality-improvement-through-test-driven-development-results-and-experiences-of-four-industrial-teams) reported lower defect density, along with longer initial development time, in four industrial teams using TDD. These methods still have value in the AI era. What changes is how we put them into practice; the basic logic of producing software remains. I want to use AI to improve mature engineering methods. When AI produces much of the code, the developer needs to design the harness: clear boundaries and rules for its work. What I want to reorganise is where the developer spends their attention and who accepts the work. With much of the implementation delegated to an agent, I need to set the scope, ask it to show what it checked, then decide whether to accept it. Problems found there should inform the next task and the project rules. Adding more handoffs and repeated reviews without solving a real problem could simply spend the time we saved.

As code generation gets faster, I think the work before and after it needs more attention: breaking down requirements and checking the result. [Cui et al.](https://demirermert.github.io/Papers/Demirer_AI_productivity.pdf) found increased task completion in three field experiments with a code-completion assistant. In an observational study at one company, [He et al.](https://arxiv.org/abs/2607.01904v2) reported more PR output alongside more work for reviewers. So I would count review and rework alongside task completion and PR output. What matters to me is how much work actually reaches a result I can accept and deliver.

First, there is the work of breaking down requirements. Since prompt engineering became popular, people have paid a lot of attention to writing good prompts. I think more of the important work happens before sending the instruction: have we worked out what we want, how we plan to build it and how we will check it? Clearer requirements and technical plans give AI a better chance of producing what we want. In a study of four game applications, [Villamizar et al.](https://arxiv.org/abs/2609.29208) found that more requirement-quality problems were generally associated with more failures in tests of generated code. Requirements without those problems could still produce faulty code.

Then there is testing and acceptance. I see two sides to this: AI's progress and AI's risks. For tasks with clear rules, having AI write automated tests is useful. Meta's [TestGen-LLM](https://arxiv.org/abs/2402.09171) is an example: it generates improvements to existing tests, then checks whether they build, run reliably and increase coverage. It discards tests that fail on the current implementation, so its main purpose is to protect existing behaviour against later changes. A person still needs to decide whether that behaviour is what we wanted.

At the same time, AI-generated code can start to feel like a "black box". If a developer hands a large amount of code to an agent and only looks at the result, without keeping up with its important assumptions, it becomes hard to know why it works or where it might fail. If AI then writes tests from the same understanding, the code and tests could agree while both get the requirement wrong. [Google's review guidance](https://google.github.io/eng-practices/review/reviewer/looking-for.html) also asks reviewers to check that tests are useful and will actually fail when the code is broken. I need to know what the tests checked, use the product and see whether it meets the original need.

Verification cost does need thought, especially who ends up paying it. The recent arguments about AI-generated mathematics bring this to mind. [Henry Cohn's essay](https://terrytao.wordpress.com/2026/09/15/the-technical-debt-of-ai-generated-mathematics/comment-page-1/) discusses people publishing poorly explained results, declaring the work finished and leaving others to understand and organise it. Software development has a similar problem. [Godot's contribution-policy announcement](https://godotengine.org/article/contribution-policy-2026/) describes AI making code contributions cheaper without increasing the number of reviewers or the time they have. Godot responds by substantially restricting AI use. In my own project, I would address this through the workflow. If the person generating the work gets the benefit while someone else pays to verify it, there is a problem with that productivity gain. Other people's time still counts as a cost.

I think having AI review AI will be an important direction. But using a new black box to review the original black box does not reassure me if all it adds is another "looks fine". [OpenAI's practitioner report](https://alignment.openai.com/scaling-code-verification/) describes better review when models can inspect the repository and execute code. It also stresses reducing false alarms, which people otherwise have to spend time checking. Meanwhile, [Jin and Chen's preprint](https://arxiv.org/abs/2603.00539) finds that models can judge correct implementations as wrong in programming benchmarks; asking for more explanation sometimes increases those mistakes. These reports point me toward a reviewer that checks its judgement against the repository and execution results. A longer explanation on its own cannot replace that evidence. I want the reviewer to show the relevant code, the requirement it breaks and how to reproduce the problem. When the process includes many supporting shell commands and pieces of code, it can be difficult for a person to follow why a change was made. Turning that into something readable and checkable should itself be part of the workflow.

Does higher review cost cancel out faster production? At least, it does not make me think we should give up AI coding. We have many ways to control that cost. During iteration, we can choose checks relevant to the change and expand them when shared interfaces or earlier assumptions change. Before committing or releasing, we can run the full integration checks. We do not need to run everything at every intermediate step, but the final gate needs to stay. I want a more efficient process that still delivers something usable and maintainable. Time spent on review and rework belongs in that calculation.

Finally, there is the developer's role. Alongside being the final decision-maker, I see two important roles: workflow maintainer and explorer. The workflow should not always be exactly the same template. Every developer has their own working and thinking habits, and the workflow should be adjusted to them. For example, I tend to work on several things at once, studying other material while an AI coding task is running. This means I need a relatively isolated working environment. In Wayline, I restricted when local voice-browser tests run so that microphone and speaker tests interrupt my other work as little as possible. Voice changes still need those tests, and the pre-commit non-voice checks and full CI remain in the [project rules](https://github.com/comp4020-agentic-coding-studio/comp4020-final-lyclccylcq/blob/0b8df75d7ecd0870ebc4d8681b26158fd329d9f0/CLAUDE.md#before-calling-something-done). AI is a tool. A good workflow should make that tool easier to work with.

Maintenance also means updating the process. The course project's CLAUDE.md records the constraints, workflow and habits that gradually developed through practice. Those habits will keep changing as experience builds up. After an agent makes a mistake, fixing it once should lead to some thought about avoiding it next time. Perhaps the requirement was unclear, a test was missing or a rule was out of date. Keeping that experience in the workflow is more useful than explaining the same problem again each time.

Exploration is the direction I want to take next as a developer. As AI frees up more time for me, I increasingly feel like a "developer + product manager". The same "classic" demo projects that turn up everywhere appeal to me less when implementing them no longer has such a high technical barrier. I care more about whether the product has its own ideas and whether anyone needs it. How to use my creativity, and how to spend more time on meaningful decisions and exploration, are the things I want to think about next. For me, that is what makes an agentic workflow good: AI takes on more of the implementation, verification keeps up, and the developer has more room to make the decisions that give the product its purpose.
